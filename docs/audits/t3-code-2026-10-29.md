# T3 Code source audit: private input and useful product gaps

Inspected the clone at `/home/shulgin/t3code`, commit
`08a463e2` (`pingdotgg/t3code`, 2026-10-29). This is a focused source review,
not a penetration test or a claim to have audited every T3 feature.

## Sensitive-input findings

- `apps/server/src/secrets/SecretRequests.ts` and its tests bind secret refs to
  a project, enforce a 24-hour TTL, serialize one-use consumption, and record
  request status rather than the answer. A cancelled/expired request closes its
  card; references are not arbitrary readback handles.
- `packages/contracts/src/orchestratorMcp.ts` and
  `apps/server/src/mcp/toolkits/orchestrator/tools.ts` expose `request_secret`.
  Default delivery returns a one-use reference. Explicit `delivery: "file"`
  instead returns a private file the agent's shell can read; that is a different
  trust boundary, not a guarantee that an agent can never obtain the value.
- `apps/server/src/auth/ServerSecretStore.ts` uses an owner-only directory and
  private files. Do not confuse file permissions with encryption at rest.
- `apps/server/src/serverSettings.ts` and `settingsSecrets.ts` keep sensitive
  provider settings in server secret storage and return redacted settings to
  clients. This write-only-client pattern is worth extending in Borg.

### Borg changes from this review

1. Private provider input is isolated from the normal composer, resumable draft,
   history, undo, copy and command interpretation. The normal draft is restored
   after the private interaction. GUI input-method context cannot read private
   text back. Provider-header JSON is masked too.
2. Sensitive provider replies are redacted before resolution events are
   journaled. Remote answer receipts use keyed intent commitments instead of
   offline-guessable bare hashes. Rotating relay authority makes old answer
   retries fail closed; it never replays an answered request. Streaming command
   output is scrubbed on complete lines before journaling, with split-key and
   multi-line private-key protection; this is not general password/PII detection.
3. First-party `request_secret` accepts a provider ID and purpose, not a secret.
   A live human enters the API key privately; Borg writes only the selected
   provider credential slot and returns a receipt. No raw answer is forwarded
   to the provider/model control channel. Requests can expire or be declined.
   OpenAI billing needs an explicit lane when saving a key could otherwise
   activate API billing. Custom-provider keys are visible as set in Settings
   and can be cleared there. Credential writes/clears are atomic and locked.
4. This intentionally does **not** introduce a general password/card vault,
   a model-readable secret lookup tool, or a shell-readable file as the default.
   New key requests fail closed on platforms without enforced private-file
   permissions. Financial PINs, CVVs and payment-card details belong in the
   original payment application's human flow.

Existing inline config keys and the credential store are permission-protected
local plaintext, not encrypted storage. A Full Access agent or another process
with the same user's authority can read local files; this is not a sandbox
against a malicious agent. Generic external provider questions may deliver the
answer to that provider even when the local UI is masked. Use the first-party
API-key request for provider setup, and the original application for passwords,
financial authentication and payments. Earlier history, sidecars, exports and
backups are not silently rewritten: rotate any key previously exposed there.

## Other additions worth considering

| Priority | T3 evidence | Borg recommendation |
| --- | --- | --- |
| High | `serverSettings.ts`, `settingsSecrets.ts`, `auth/ServerSecretStore.ts` | Finish a write-only secret-settings API: return presence/source metadata to clients, never existing secret values. Add an OS-keychain/secret-service backend and explicit fallback policy rather than pretending local files are encrypted. Keep account/provider-instance scope visible. |
| High | `SecretRequests.ts`, `scheduledTasks/ScheduledTaskService.ts` | Extend destination-bound secret consumption only when there is a real typed consumer, e.g. a specific webhook signature. Add expiry, scope and replay tests before introducing general refs. Avoid stranded refs with no consumer and do not make shell/file access the default. |
| Medium | `packages/provider-opencode/src/server/status.ts` and provider option descriptors | Render provider capability descriptors as typed settings controls: model-specific enums, booleans, numeric ranges and help, rather than requiring JSON for every advanced model option. Retain Borg's own loop and routing policy. |
| Medium | `scheduledTasks/ScheduledTaskService.ts`, `scheduling/Scheduler.ts` | Put scheduled runs, destination, next execution, missed runs and pause/cancel in a user-facing screen on top of Borg's existing goals/watchers/workflows. Bind webhook credentials to typed consumers and keep payment/security actions human-confirmed. |
| Medium | `checkpointing/CheckpointStore.ts`, `CheckpointDiffQuery.ts`, `docs/user/source-control.md` | Improve checkpoint/diff/restore UX with a scoped preview of affected files. Reuse Borg's journal and Git ownership rules; never overwrite unrelated user work with a blanket revert. |
| Later | `docs/user/snap-shot.md` and desktop capture setup | Add a user-initiated window-capture shortcut and clear accessibility-text/privacy toggles. Borg already has model-side desktop tools; the gap is human onboarding and capture UX. Images can still contain sensitive data—do not promise automatic payment/PII sanitization. |
| Later | `orchestration-v2/ThreadForkService.ts`, `ProviderSessionTransitionPolicy.test.ts`, `docs/user/portable-handoffs.md` | Add a clear portable-handoff preview on top of Borg's canonical history, including what transfers, what is omitted and which local secret references cannot transfer. |

Do not import another product's agent loop, account telemetry, or permissive
secret-file delivery simply for feature parity. The useful patterns are explicit
user choices, scoped authority, safe server-side consumption and good controls.
